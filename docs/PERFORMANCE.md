# 为什么慢：抽取性能剖析与优化

> 结论先说：我们不是「读得慢」，是**写得太多、而且是串行写**。
> 直接让 AI 总结是「压缩」（一段话，~170 tokens）；我们是「结构化抽取」（每块几千 tokens 的 JSON）。

## 1. 实测对照（同一段 3500 字原文，deepseek-flash）

| 方式 | 耗时 | 输出 |
| --- | --- | --- |
| ① 直接总结（200 字以内） | **4.1s** | 270 字符（~170 tokens） |
| ② 我们的结构化抽取（优化前） | **81.9s** | 15,587 字符（~9,700 tokens） |
| ③ 我们的结构化抽取（收紧后） | **21.9s** | 3,846 字符（~2,400 tokens） |

时间基本正比于**输出 token 数**：生成速度约 25–30 tokens/s，写 9,700 tokens 就要 80 秒。

## 2. 慢的三个原因

1. **输出规模大**：每个块要求 10–20 个节点，每个节点带 summary / quote / aliases / 四问 / 自测 → 一块上万字符。
2. **逐块串行**：15 页 = 5 块 × ~80s；300 页 = 100 块 → 数小时（大部分时间在等网络，不是算力）。
3. **插件桥接没有传 `maxTokens`**：模型没有输出上限，容易「自由发挥」写长文（独立运行时反而会被 4000 截断 → JSON 非法）。—— 已修：现在把请求里的 `maxTokens` 传进 `prepareCall` 的 `callConfig`。

## 3. 已做的优化

| 优化 | 效果 |
| --- | --- |
| 收紧 prompt：每块 ≤6 节点、summary ≤40 字、quote ≤80 字；四问/自测**只给 importance ≥4 的节点写** | 单块 81.9s → **21.9s**，输出 ↓76% |
| 块级**并发 3 路**（可配 1–8） | 墙上时间再 ↓ 约 3×（受 provider 限流约束） |
| 章节速览失败后可直接「重试整理」（不刷新页面）+ 去掉重复提示文案 | 模型偶发只回推理 chunk 不给正文（实测 ~1/4 概率空输出）；插件返回 503，客户端自动重试一次 |
| **把 `maxTokens` 传给宿主 LLM**（`LlmCallConfig.maxTokens`） | 之前插件桥接没传，模型无输出上限，「整理这一章」会写到停不下来；现在 extract/chat 两条路径都受上限约束 |
| 两阶段汇总（>80 节点分批 80 → 最终汇总） | 避免大文档单次 reduce 被截断/超时 |
| 超时 90s → 300s，最终汇总失败保留批次结果 | 大文档不再「整篇归零」 |
| 块级缓存（key = 文档 + 块哈希 + prompt 版本） | 重抽/章节拆解 0 次新调用 |

**实测（2026-11-25，deepseek-flash，插件内进程调用）**：
- 15 页论文全局抽取 **157s**（maxTokens 未生效前 >900s 仍未完成）；
- 「整理这一章」**42s**，产出约 1600 字分段速览。

**估算**：15 页手册 ≈ 5 块 → 约 **1.5–2 分钟**；300 页 ≈ 100 块 → 约 **20–40 分钟**（并发 3）。

## 4. 代价（诚实说明）

- 每块最多 6 个节点：细节粒度变粗；缺失的细节可以在节点上「点击进一步分析」按需补；
- 四问/自测不再对每个节点生成：只给重要节点写，其余懒加载；
- 并发 3 路：provider 限流时可能排队，代码已按单块失败可重试设计。

## 5. 还能更快（未做）

1. **按章懒加载**：只抽用户点开的章节（章节子图本来就有缓存，本质已具备）；
2. **map 阶段换更小的模型**：结构化抽取比「理解」更吃指令遵循，小模型可能够用；
3. **流式增量**：边抽边显示节点，缩短「看起来在等」的时间（不减少总耗时）。
